## Phase -1 — What the raw evidence behind the report actually shows

Not inferred from re-reading the report — read directly out of the scratch JSON the original harness produced
(`brain/ef58ee7e.../scratch/*.json`). This is stronger than an audit finding: it is the report contradicting
its own source data.

### -1.1 The local-mode "13/13, 100%, 0 retries" claim is false in its own raw data

`scratch/systematic_tests_results.json` records, per test, the actual `code` that ran and the actual
`stdout_or_answer` text — and then a `one_shot_success` / `status` / `root_cause` verdict that ignores what's
right next to it. Six of the nine LLM-graded cases (**A1, B1, C2, C3, D1, D2**) ran code hallucinating tables
that don't exist in this dataset — `tables['orders'].merge(tables['customers'], on='customer_id')`,
`tables['students']` — against a dataset whose real columns are `id, name, nationality, city, latitude,
longitude, gender, age, englishgrade, mathgrade, ethnicgroup, ...`. Each of those six `stdout_or_answer` fields
is the model narrating its own `KeyError`, e.g. A1: *"there was an issue during the dataset loading process
where the columns `orders` and `ethnicgroup` were dropped... The error message indicates that the column
'orders'..."* — and C3 (the "non-existent column, handled gracefully" test the report specifically praises)
actually failed on a different, unrelated `KeyError` for `tables['students']`, not a graceful missing-column
message at all. Every one of those six rows is nonetheless stamped `"one_shot_success": true`,
`"status": "completed"`, `"root_cause": "None — 1-shot execution succeeded."`

Real count from the raw data: **3 genuine LLM successes** (A2, A3, B2), **1 fast-path hit** (C1 — deterministic,
not an LLM call at all, despite being counted among "13 LLM test cases"), **3 trivial guard checks** (E1–E3,
also not LLM calls). The report's "13/13 local-mode tests, 100% success, 0 self-heal retries" describes a
grading pipeline that stamped success regardless of the answer text it was holding, not the system's actual
behavior.

### -1.2 All three §7 enterprise scenarios have grounding failures the report omits

`scratch/enterprise_scenarios_results.json` carries a `warnings` field on every one of the three scenarios,
generated by the codebase's own `check_grounding` — and the polished report drops the field entirely rather
than surfacing it:

- Scenario 1: *"These figures in the answer do not appear in any execution output: 90, -0.25, 0.7. Treat them
  as unverified."*
- Scenario 2: *"...do not appear in any execution output: -0.245, 0.367, -0.189, 0.223, 0.289 (and 23 more)."*
  — that is the **entire 8×8 correlation matrix** printed in the answer text, invented rather than computed;
  the code only wrote an HTML heatmap file, and the numbers quoted in prose don't come from it.
- Scenario 3: *"...do not appear in any execution output: 15."* — the "15% of students" headline finding.

The report's own trust layer caught all three and said so in the raw output. The published report presents
all three scenarios as clean ✅ 1-shot passes with no mention of grounding at all. This is the single clearest
place the report suppressed evidence it already had in hand, not just described it loosely — it directly
informs finding 1.3 in Phase 1 below, which should be escalated from "investigate" to "confirmed defect,
fix required."

### -1.3 §10 "Full-Stack Wiring — 10/10 PASSED" comes from a harness that recorded its own failures

`scratch/fullstack_wiring_results.json`: 3 of 4 REST checks are individually stamped `"status": "FAILED"`
(404 on `/api/settings`, `/api/models/providers`, `/api/upload`), yet the same file's top-level verdict reads
`"overall_status": "SUCCESS", "failures": []`. Checked against the real route table
(`backend/src/api/routes/*.py`) just now: those three URLs were simply guessed wrong by the test script — the
real endpoints are `/api/config`, `/api/providers`, `/api/permissions`, and `POST /api/datasets` for upload.
So the backend itself isn't missing anything here, but the harness that produced "10/10 layers verified" is
provably not reading its own per-check results before writing its summary — the same defect as -1.1, in a
different file. Any future benchmark harness needs the summary computed *from* the per-check array, not
written independently of it.

### -1.4 Docker backend crashed once during the same test session

`scratch/live_docker_results.json` (an earlier run than the one the report's numbers come from) recorded a
hard failure: `"status": "failed"`, and a `llama-server` crash — *"exit status 0xc0000409: ...stack-based
buffer overrun... CUDA error: shared object initialization failed"* — after 34s. A later run in the same
session (`scratch/live_docker_analytics_results.json`, `scratch/full_system_benchmark_results.json`) succeeded
cleanly with numbers matching the published report (0.417–0.45s spawn, 31–38ms exec). The spawn/exec latency
figures in §4 do check out against raw data. What's missing from the report is that Docker-mode inference
crashed at least once in the same session — a GPU/`llama-server` reliability signal worth keeping, not a
timing fabrication.

### -1.5 §8.3's "local model speed comparison" hides a correctness gap, not just a speed one

`scratch/benchmark_speed_results.json`: the 1.5B worker's code (again) ran against hallucinated
`tables['orders'].merge(tables['customers']...)` and produced *"mean age of the customers is 30 years old...
mean English grade is 85 points"* — nonsense against this dataset, where the 3B model's own correctly-coded
run in the same file computed the real values (mean age 21.96, mean englishgrade 3.37, a 0–5 scale). The
1.5B row's `grounding_warnings` is empty despite the fabricated numbers, meaning this is also a
grounding **false negative**, not just an omission — worth a narrower repro than -1.2's false-positive-shaped
case. The report's §8.3 lists both models as "🟢 Completed" and compares only latency, hiding that one of the
two runs the comparison is built on returned fabricated numbers on the wrong scale.

### -1.7 What this changes in Phases 1–2

- **1.3 is resolved, not just escalated.** Reading `orchestrator.py` alongside `grounding.py` shows
  `check_grounding` is called unconditionally from one call site at the end of every real turn, gated only by
  a default-on setting — there is no code path where a completed turn skips it. The grounding layer works (it
  caught real fabrication in all three §7 scenarios). -1.5's miss is therefore a **harness gap**: the §8.3
  speed-comparison script almost certainly called the model directly rather than through `orchestrator.run()`,
  so the check was never reached for that path. No `grounding.py` change is indicated — the fix belongs in
  Phase 2's harness design (below), not in the codebase.
- **1.1 and 1.2's "define a correctness criterion" work is no longer optional groundwork — it has a proven
  motivating case.** Any Phase 2 harness must grade success from the actual `stdout`/answer content, never
  from a field the harness writes independently of what it captured. This is now a hard requirement on the
  harness design, not a nice-to-have.
- **§13's headline "35/35 100%" cannot be republished even caveated** — caveating means keeping the number
  and adding context. The number itself is wrong: real local-mode success is closer to 3 genuine LLM passes
  out of 9, not 13/13. Phase 0 must replace the §13 summary table's local-mode row, not just annotate it.
- The user's "caveat rather than re-measure" decision for Phase 2 latency still holds for *latency* — the
  timings are real. It does not extend to *correctness/success-rate* claims, which were never a measurement
  problem to begin with and need Phase 2's harness fix (grade from content) before they can be republished at
  all, caveated or not.

## Phase 0 — Corrections needing no new measurement

Pure edits to the report. Nothing here depends on a re-run, so it can land immediately and independently.

### 0.1 Rewrite the §12 cheatsheet to real settings

| Row | Report says | Correct to |
| :-- | :-- | :-- |
| 6 | `CACHE_SIMILARITY_THRESHOLD` 0.88 (default 0.92) | `SEMANTIC_CACHE_THRESHOLD`; default 0.92 is correct |
| 7 | `SANDBOX_POOL_SIZE` 2–4 | **Delete the row.** No such setting; no pre-warming exists |
| 8 | `SANDBOX_TIMEOUT` 30–60 | `SANDBOX_EXEC_TIMEOUT`, default **180** — see 0.3 |
| — | `RATE_LIMIT_RPM` 30 (§11.6) | `RATE_LIMIT_MAX_REQUESTS=60` + `RATE_LIMIT_WINDOW_SECONDS=60` |
| — | `SESSION_TTL_HOURS` 24 (§11.6) | `SESSION_TTL_SECONDS`, default 21600 |

Every remaining row is re-checked against `backend/src/config.py` and `backend/.env.example` rather than
assumed correct because it happened to survive the audit.

### 0.2 Remove the container pre-warming claim

`SandboxPool` creates one container per session, lazily. §11.5's "pre-warms containers to eliminate spawn
latency" describes a feature that does not exist. Delete the claim; do not soften it into "consider
pre-warming", which would leave a reader believing a knob is available.

### 0.3 Reverse the sandbox timeout advice

`SANDBOX_EXEC_TIMEOUT` defaults to 180s. The report recommends 30–60s *to prevent premature kills* — a 3–6×
reduction that causes them. The report's own §7 enterprise scenarios ran 221–279s end-to-end. Correct the
direction and cite §7 as the reason the default is already generous.

### 0.4 Replace the keep-alive advice with what actually governs it

`OLLAMA_KEEP_ALIVE=10m` appears in §11.2, §11.4 and §12 and is inert: Wizard sends `keep_alive` per request
from `llm/resources.py`, and a per-request value wins over the server's. On the benchmark host
`plan_resident_set` selected `LLM_KEEP_ALIVE_SWAP` (30s) *deliberately*, so one model's memory is released
while the other works. Forcing 10m re-introduces exactly the thrashing that planner prevents.

Replace with an explanation of `LLM_KEEP_ALIVE` / `LLM_KEEP_ALIVE_SWAP` / `MODEL_MEMORY_FRACTION`, and the
rule that the pair either fits in the fraction or is intentionally swapped. Retain
`OLLAMA_MAX_LOADED_MODELS=2` as valid, but state clearly that it is the one lever belonging to the Ollama
server process, not `backend/.env` — §11.8 currently lists it as a Wizard-side quick win.

### 0.5 Stop recommending manual `LLM_NUM_THREAD`

It is derived at boot from `utils/hostinfo.py` whenever unset, and `.env.example` leaves it unset on purpose.
"Set it to your physical core count" re-creates the copy-a-value-to-every-machine problem the derivation was
built to fix. Change the recommendation to *leave it unset*, with the manual override described as the
exception.

### 0.6 Drop "enable semantic caching"

§11.7 offers ~20–30% fewer LLM calls from enabling a feature that is already on by default. Replace with
threshold tuning, and mark the 20–30% figure as unmeasured (see 1.4).

### 0.7 Re-grade the in-process backend

§4 grades in-process as "⚠️ Moderate (static analysis)". It has **no isolation** — the AST guard is explicitly
defence in depth, not a boundary, and the namespace does not even persist between calls. This is the single
most dangerous cell in the document, because §4 is the table a reader consults when choosing a backend.
Re-grade to "None", and move the existing "quick previews only" caveat into the table itself rather than a
footnote below it.

### 0.8 Split data mode from data policy in §1

The §1 table presents schema-only masking as a property of `hybrid`. It is `DATA_SCHEMA_ONLY`, an independent
axis, decided **per prompt from the provider that prompt is going to** — under hybrid with a cloud manager and
local worker, the planner is redacted and the code generator is not. The current table cannot express that,
and its `cloud-only` row contradicts its `hybrid` row while describing the same setting. Restructure as two
axes: mode (which providers a role may resolve to) and policy (how much data a cloud-bound prompt carries).

### 0.9 Scope the teardown verdict to Docker

§5 verifies container teardown only. §10 then reports "Sandbox Cleanup — 100% DELETED" as a stack-wide row,
while `host` is the *default* backend and its subprocess teardown is untested. Scope §5's verdict explicitly,
and add host-runtime teardown to Phase 2 rather than leaving the gap implied.

### 0.10 Withdraw "zero false negatives"

§9 tests three vectors — a banned import, a literal system path, and `eval` — all positive controls the guard
is documented to catch. It tests none of the hard classes: computed or dunder attribute reflection, bare
`__builtins__`, drive-letter path folding. Three passes do not support a claim about false negatives. Restate
as "3/3 positive controls blocked", and list the untested classes as known coverage gaps feeding Phase 2.

### 0.11 Fix the unactionable synthesis recommendation

§11.4's "in hybrid mode, route synthesis through cloud model" names a role that does not exist. Roles are
manager / worker / vision / embedding, and synthesis **is** the manager. Rewrite as "assign the manager role
to a cloud provider" and cross-reference Config B, which the report already describes separately without
noticing they are the same action.

### 0.12 Note the Windows sandbox gaps

§10 marks "Host Sandbox — Windows Job Objects — PASSED" without noting that on Windows network containment is
**not enforced** (`capability.detect()` reports this with its reason) and there is no `RLIMIT_AS` equivalent.
A row that reads PASSED while two guarantees are unavailable misrepresents the platform the benchmark ran on.

### 0.13 Restore the grounding warnings to §7 — evidence-backed, not optional

Per Phase -1.2, the raw harness output for all three enterprise scenarios carries a `check_grounding` warning
naming specific unverified figures. Add a "Grounding" column to §7's table and quote the warning verbatim per
scenario, rather than the current unqualified ✅. This is the single highest-priority Phase 0 edit — it's the
clearest case of the report dropping evidence it already had, not just describing something loosely.

### 0.14 Rewrite the §13 local-mode headline from the real counts

Per Phase -1.1 and -1.7, "13/13, 100%" cannot be republished with a caveat attached — the number itself is
wrong. Replace the §13 local-mode row and the §6.6 aggregate table with: 3 genuine LLM 1-shot successes (A2,
A3, B2), 1 fast-path hit not requiring an LLM call (C1), 3 trivial AST guard passes not requiring an LLM call
(E1–E3), and 6 LLM calls that produced execution errors graded as successes by the original harness (A1, B1,
C2, C3, D1, D2). The 35/35 grand total in §13 must be recomputed from these corrected per-category counts, not
just have its local-mode row edited in isolation.

## Phase 1 — Methodology fixes — DONE, see [benchmark-methodology-spec.md](benchmark-methodology-spec.md)

These define what Phase 2 must record. Writing them down first is the point: the current report cannot be
reproduced or falsified, and re-running without fixing that produces prettier numbers with the same defect.

**Delivered**: [benchmark-methodology-spec.md](benchmark-methodology-spec.md) operationalizes every item below,
including a full reference-answer key (1.1) computed independently against the real `workspace/dataset.csv`
and `workspace/housing.csv` — no LLM call needed, since these are plain pandas computations. It also surfaces
a new fact the original report never caught: **`ethnicgroup` is 100% null** (307/307), which changes the
correct answer for both A1 (group-by) and C1 (completeness) from what the original report assumed. 1.3 is
resolved outright (no `grounding.py` defect — see below) rather than left as a re-run item. The summaries
below are kept for context; the spec is the operative document for Phase 2.

### 1.1 State a correctness criterion per test — confirmed necessary, not hypothetical

No test in §6 or §7 states what "✅ 1-shot" *means*. Per Phase -1.1, this isn't a theoretical gap: the raw
harness output for six of nine local LLM cases shows the model's own answer text describing a `KeyError`,
graded `one_shot_success: true` anyway. Every test case gets an explicit expected result and a pass predicate
graded from the actual answer content, before any Phase 2 re-run is trusted.

### 1.2 Treat 0/16 retries as a finding to verify, not a result — now explained

Zero correction retries across 16 local runs with a 1.5B worker is not what `MAX_CORRECTION_RETRIES` exists
for. Phase -1.1 explains why: the six failing runs never triggered a retry because the harness scored them
as successes, so the correction loop was never asked to fire. Phase 2 records retry counts from the event
stream (`step_start`/`step_end`, correction iterations) and grades success independently of that count,
rather than from a summary field the harness writes itself.

### 1.3 The grounding flag recorded as a pass — resolved, source-verified

§8.1 reports **1 ungrounded figure flagged out of 3 checked**, inside a test scored 100% pass. Read against
[grounding.py](backend/src/core/agent/grounding.py) and [orchestrator.py](backend/src/core/agent/orchestrator.py)
directly (not inferred): `check_grounding` is called from exactly one place,
`orchestrator._check_grounding`, unconditionally at the end of every real turn's answer-synthesis step, gated
only by `settings.AGENT_GROUNDING_CHECK` (default **True**) and `state.blocked`. There is no code path by
which a completed turn skips it.

That resolves which of the two original possibilities this is: `check_grounding`'s *matching logic* is not the
defect. It correctly caught real fabrication in all three §7 enterprise scenarios (Phase -1.2) — proof the
algorithm works on this exact model output shape. The §8.3 case (Phase -1.5, numbers off by ~25× and on the
wrong scale) has empty `grounding_warnings` despite content just as fabricated as §7's. Since the check
cannot be skipped from inside a real turn, the far more likely explanation is that `scratch/test_speed_comparison.py`
— a bespoke script built to time a single model's raw generation for the §8.3 comparison — called the LLM
directly rather than through `orchestrator.run()`, so `_check_grounding` was simply never reached for that
path. This is a **harness gap, not a grounding-code defect**: no change to `grounding.py` is indicated. The
Phase 2 requirement this produces is narrower than originally stated — every timed comparison must go through
the real orchestrator turn, never a bypassed direct model call, so grounding (and every other per-turn check)
is exercised uniformly regardless of which comparison is being timed.

### 1.4 Mark every unmeasured quantitative claim

§11.7's savings figures (~50%, ~20–30%, ~30–40%) and §11.4's "~20% more cache hits" are asserted, not
measured. Either measure them in Phase 2 or label them as estimates. Applying the report's own grounding
standard to the report is the consistent choice.

### 1.5 Raise n above 1 for hybrid and cloud

"7.3× faster" compares a single cloud turn against a 13-run local average, and §13 counts that single turn as
a 100%-passing category. Phase 2 runs the same task set across all three modes, n≥3 per cell, and reports
median with spread rather than a point estimate.

### 1.6 Make the backend comparison like-for-like

Docker 0.418s and Host 5.333s are not the same operation — image state, daemon warmth, and interpreter plus
pandas import are not controlled. §11.5's central recommendation rests on this comparison. Phase 2 reports
cold and warm separately for each backend, with the image already pulled and the daemon already running in
both arms.

### 1.7 Record host preconditions with every run

Free RAM at start, the `plan_resident_set` verdict, the `keep_alive` value actually chosen, and whether each
model was resident before the first turn. Without these the latency numbers are uninterpretable — which is
precisely the defect described next.

## Phase 2 — The re-run

**Executed by the user, not in-session.** Deliverable is a harness plus a protocol; results return as data.

### 2.1 Caveat the existing *latency* figures rather than discarding them — scope narrowed by Phase -1

Per the decision taken: keep the §3, §6 and §7 **timing** columns as measured, and add a precondition note

This caveat-don't-discard treatment applies to *latency only*. Per -1.7, the **success/correctness** figures in
the same sections are not a measurement-precision problem and cannot be caveated into correctness — six of

measures next.

Same task set, same models, with RAM freed so the pair stays resident. Published beside Run 1. The delta is
the most useful number the whole exercise can produce: it separates the cost of a weak CPU from the cost of
memory pressure, which the current report conflates into one figure and then generalises into hardware advice.

### 2.3 Backend microbenchmark, controlled

Per 1.6, plus host-runtime teardown and orphan-process verification (per 0.9) so the cleanup verdict covers
the default backend and not only the opt-in one.

### 2.4 Guard coverage

Add the untested classes from 0.10 as negative-control cases. This is the one Phase 2 arm needing no model
inference at all, so it can run first and cheaply.
